# TeleBot 产品需求文档（作品集版）

> 产品定位：通过飞书连接手机与电脑的受控 AI 助理  
> 文档版本：V1.0｜2026-09-30  
> 阶段：个人日常使用中的可运行原型；本文将已实现能力与建议验收目标分开陈述  
> 项目角色：独立完成产品定义、交互设计与原型开发  
> 项目形态：从个人跨设备文件操作起步，逐步扩展项目知识库与本机 Codex

## 1. 一页摘要

用户离开电脑后，仍会想查看电脑上的文件、整理资料或继续处理代码任务。传统远程桌面在手机上操作繁琐，直接把系统权限交给聊天机器人又容易误读指令。TeleBot 以飞书 Bot 作为跨设备消息通道：用户从手机或其他设备发送请求，由运行在电脑上的 Agent 访问受控文件空间、交付文件或调用本机 Codex；后来增加的项目知识库，让资料也能被检索和复用。涉及导入、覆盖、删除和执行的操作，系统先展示范围，再由发起人确认。

产品核心判断：**跨设备交互的价值在于把“发出意图”和“在电脑上完成任务”连起来，同时让用户始终知道系统会动哪些资料、做哪些操作。**

## 2. 项目背景与问题定义

### 2.1 目标用户

| 角色 | 典型任务 | 当前摩擦 |
| --- | --- | --- |
| 个人开发者/知识工作者 | 在手机上查电脑文件、获取报告、继续处理本机任务 | 离开电脑后难以高效操作本地资料；远程桌面不适合碎片化任务 |
| 项目空间管理员 | 把本机或飞书资料纳入知识库并控制访问 | 文件分散，导入范围与访问对象需要明确 |
| 项目成员 | 查项目资料、追问背景、获取报告 | 资料靠人转发，回答难核对来源 |

### 2.2 需要解决的三个问题

1. **设备割裂**：人在手机端，资料和开发环境在电脑端，简单任务也要回到电脑前完成。
2. **资料难复用**：本地文件与飞书资料分散，查找和再次利用缺少统一入口与来源线索。
3. **执行不放心**：AI 可以完成复杂任务，但读取、导入、覆盖、删除和代码执行需要明确的权限与确认机制。

以上为基于项目场景形成的产品假设；当前仓库没有用户访谈、真实使用规模或节省时长数据，不能把它们写成已证实的用户结论。

### 2.3 产品演进

| 阶段 | 用户需求变化 | 产品能力 |
| --- | --- | --- |
| 起点 | 离开电脑时，仍能通过手机处理电脑上的文件和任务 | 消息入口、受控本地文件工具、报告与文件回传 |
| 扩展一 | 文件越来越多，需要把个人和项目资料沉淀为可检索知识 | 项目空间、资料导入、语义检索、来源线索 |
| 扩展二 | 仅查看资料不够，希望远程推进代码工作 | 飞书显式调用本机 Codex，先检查/规划再确认执行 |

飞书在这里是连接设备的交互层，不承载电脑文件本身；Agent 和受控工具运行在用户电脑或其部署主机上。

## 3. 产品目标与边界

### 3.1 一期目标

- 从手机等设备经飞书发起请求，在电脑端完成受控文件任务并回传答案或文件。
- 让成员只检索自己有权访问的项目空间资料，并看到可核对的文档线索。
- 让有影响的操作经过“预览影响范围 → 同一用户确认/取消 → 执行反馈”。
- 对资料索引和模型调用设置用量边界，遇到额度或解析失败时给出明确状态。

### 3.2 非目标

- 不做跨项目空间的全局检索。
- 一期不做图片 OCR、语音转写、飞书云文档自动同步。
- 不让普通自然语言自动触发 Codex 改码；代码任务须用显式 `/codex` 命令。
- 不把聊天群成员自动视为知识库成员。

### 3.3 北极星指标与验证口径（建议，尚未实测）

| 指标 | 定义 | 建议验证方式 |
| --- | --- | --- |
| 跨设备任务完成率 | 用户从非电脑设备发起请求后，得到可用答案、文件或执行结果的比例 | 标注一组真实任务，人工评估结果与来源 |
| 首次有效响应时长 | 从飞书消息到首条有意义反馈的耗时 | 记录 webhook 收到与反馈时间 |
| 来源可核对率 | 知识库回答中能定位到原文档与片段的比例 | 抽样核对引用和原文 |
| 高风险操作确认覆盖率 | 应确认操作中先展示预览且由原用户确认的比例 | 审核操作日志与异常案例 |
| 单空间日成本 | 对话与 Embedding 调用的实际账单成本 | 与本地用量记录、供应商账单对账 |

不设置虚构的提升百分比。试点后再确定目标值与基线。

## 4. 产品方案

### 4.1 信息架构

```text
手机或其他设备 → 飞书 Bot → 运行在电脑上的 TeleBot
├─ 本机任务：受控文件读取、报告输出、文件回传
├─ 显式 /codex：inspect/plan/apply → 本机代码工作区
└─ /kb 项目知识库
   ├─ 项目空间与成员
   ├─ 资料导入：允许目录、飞书附件、显式云文档链接
   ├─ 检索：当前会话绑定空间 + 当前提问者成员资格
   └─ 管理：目录绑定、成员变更、删除、用量查看
```

### 4.2 关键用户旅程

**旅程 A：人在手机上，获取电脑中的文件或报告**  
用户在飞书向 Bot 提出文件或研究任务；电脑端服务在允许目录中查找、读取或生成报告；系统将简短结果或文件回传至原会话。路径不明确时先澄清候选，目标超出允许范围时拒绝操作。

**旅程 B：把分散资料变成可查知识库**  
管理员绑定允许目录或提交文件/飞书 docx 链接；系统展示待导入范围和文件清单；管理员点击确认或回复确认；系统解析、去重、索引并反馈成功、未变化、失败数量。格式或权限不符合要求时给出原因。

**旅程 C：离开电脑后继续本机代码任务**  
用户通过飞书用 `/codex inspect` 了解电脑上的工作区，或用 `/codex plan` 生成变更方案；进入 apply 前查看计划和影响范围；确认令牌绑定会话与发起人，确认后在电脑端执行并返回结果。普通问答不进入该流程。

**旅程 D：成员检索项目资料**  
管理员创建空间并邀请成员、绑定会话；成员发送 `/kb search <问题>`；系统先确认会话绑定与成员资格，再在当前空间检索，返回文档标题、来源、片段位置和摘要。无命中时明确告知，不编造项目事实。

### 4.3 一期需求清单

| 编号 | 优先级 | 需求 | 验收标准 |
| --- | --- | --- | --- |
| R1 | P0 | 跨设备消息闭环 | 手机等设备经飞书发出请求，电脑端接收并处理；识别文本、文件、图片与卡片动作；重复事件不重复执行 |
| R2 | P0 | 项目空间权限 | 读取同时校验会话绑定与用户成员资格；成员不能执行管理员操作；跨空间请求拒绝 |
| R3 | P0 | 资料导入与检索 | 支持 Markdown、TXT、PDF、DOCX；只从已绑定且允许的路径导入；检索结果带标题/来源/片段位置 |
| R4 | P0 | 操作确认 | 目录绑定、导入、成员变更、删除等先预览；令牌绑定原会话、原用户且限时、单次使用；取消不执行 |
| R5 | P0 | 显式代码执行 | `/codex inspect`、`plan`、`apply` 分级；只读阶段不能改文件；执行受工作区、超时和输出长度限制 |
| R6 | P0 | 受控文件与报告交付 | 在允许目录内读取文件或生成 Markdown 报告，经飞书回传；上传前校验允许目录与大小 |
| R7 | P1 | 成本与失败反馈 | 内容哈希避免重复 Embedding；达到预算停止新索引；解析/接口错误反馈可行动原因 |
| R8 | P1 | 会话连续性 | 保留必要会话状态，重启后知识库与已索引资料仍可查询 |

### 4.4 关键规则

- **权限**：项目空间独立于飞书 chat。一个会话同时绑定一个空间；空间可以绑定多个会话。每次读取仍检查提问者是否是空间成员。
- **来源**：本地资料仅限管理员已绑定目录和系统允许根目录的交集；云文档由管理员显式导入一次，不自动同步。
- **数据边界**：资料分块和查询文本会发送给所配置的百炼 Embedding 服务；对话模型与 Embedding 凭据分开配置。需在试点前向参与者说明这一点。
- **异常**：无权限、无命中、格式不支持、目录歧义、预算耗尽和外部接口失败均返回明确提示；不能用模型猜测补全未取得的资料。

## 5. 交互要点

### 5.1 确认卡片

卡片固定包含操作名称、影响范围、确认/取消按钮。确认后给出执行结果；取消后给出取消状态。文本“确认/取消”作为兼容入口，但必须对应当前用户在当前会话中的唯一待处理操作。

### 5.2 长内容反馈

先给可读的进度或摘要，报告作为文件交付；避免在群聊连续刷出整篇长文。失败时说明已完成到哪一步、是否产生文件或索引，以及用户下一步可做什么。

## 6. 发布与验收计划

| 阶段 | 范围 | 通过条件 |
| --- | --- | --- |
| 原型验证 | 飞书消息、知识库、显式 Codex、确认卡片 | 端到端演示三条关键旅程；权限与确认测试通过 |
| 小范围试点 | 1–2 个项目空间、少量真实文档 | 记录有效任务、无命中、失败原因、用户反馈与实际账单 |
| 迭代评估 | 查询质量、导入体验、成本 | 按前述指标决定是否增加混合检索、后台索引或更细权限 |

作者已通过手机在日常场景中使用该产品，这是个人使用验证。当前仓库还可验证原型实现与自动化测试；这些证据不等同于多用户试点或量化业务效果。截至本版文档，抽查的飞书适配、知识库检索与权限、Codex 确认相关测试共 **36 项通过**；尚未据此声称整体线上稳定性或业务收益。

## 7. 产品决策与取舍

1. **用飞书连接设备**：手机端负责表达意图与确认，电脑端运行 Agent、接触本地资料和开发环境；用户可在同一会话收取结果。
2. **按项目空间授权**：群聊身份不足以代表资料访问权，读请求也需要逐人校验。
3. **显式命令加确认门**：让高影响操作可被用户识别与复核；自然语言保留给问答和低风险任务。
4. **先用 SQLite 与受限规模检索**：面向小型团队原型，降低部署复杂度；数据量、并发和检索质量增长后再评估专用检索基础设施。
5. **一期排除 OCR 与自动同步**：先把可控导入、权限和引用闭环做实，再扩大内容类型。

## 8. 作品集说明与证据

本项目由作者独立完成产品定义、交互设计与原型开发，并已通过手机日常使用。本 PRD 是基于现有项目代码、文档和项目起点整理的产品表达。可展示的证据包括：飞书事件入口与消息服务、受控文件工具、知识库项目空间和检索实现、显式 Codex 流程、确认卡片、权限与检索测试。作品集呈现时建议补充一段真实飞书演示录像，以及 2–3 个从问题到结果的完整案例；若取得试点数据，再更新指标表和结论。

项目源码中的早期 issue 与系统设计文档保留了消息通道原型的演进过程。作品集叙事应以“跨设备操作电脑”为起点，再说明知识库与本机 Codex 如何从这一核心需求延伸出来。

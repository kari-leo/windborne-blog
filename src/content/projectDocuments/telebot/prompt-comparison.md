# TeleBot 定时触发功能需求

## 一、功能定位

为 TeleBot 新增定时触发功能，使用户能够通过自然语言创建、查询、修改和删除单次或周期任务，并在预定时间由电脑端主动执行相应操作，将执行结果反馈至原交互端。

本轮优先支持基于时间的任务触发，不引入复杂的条件监控和多任务编排。

## 二、功能模块

### 1. 交互模块

设计任务设定、查询、修改、删除及执行反馈的用户交互接口。

用户可以通过特定命令或模糊自然语言唤起定时任务功能。系统应识别用户意图，将其转换为具体的任务管理操作。

- 创建：识别任务内容、触发时间、重复规则、执行方式与权限要求，展示任务摘要，并在用户最终确认后创建。
- 查询：支持查询完整活跃任务列表、指定任务和历史执行记录，无需用户确认。
- 修改：支持修改现有任务的内容、触发规则、权限等，展示变更摘要，经确认后生效。
- 删除：用户指定任务后，由系统展示待删除任务，确认后取消后续调度。
- 反馈：任务到期、申请执行授权、执行完成、失败或超时时，均应根据任务配置向用户提供相应反馈。

若一条消息包含多个任务，系统应拆分并分别展示任务详情，支持一次性确认创建。

涉及模糊时间或不同解释的任务，应在创建前澄清。例如“周六七点完成项目代码”需要明确是七点开始执行，还是要求七点前完成。

所有用户只能管理自己创建的任务。权限校验必须在实际任务管理接口中执行，不能仅依靠大模型判断。

### 2. 任务权限模式

任务创建确认与实际执行授权是两种不同的操作。用户确认创建任务，不代表自动授予未来所有操作的执行权限。

系统应支持三种模式：

**模式 A：仅提醒**

到达预定时间后，在交互端提醒用户。是否进一步执行任务，由用户主动决定。

**模式 B：预授权自动执行**

创建任务时，用户明确授权未来在指定时间自动执行。授权应限定任务内容、可访问目录、可调用的 Skills 和 MCP Tools，以及允许的操作范围。

任务到期后，系统在授权范围内自动执行，无需再次申请整体执行授权。

预授权不得绕过原有工具或操作级安全限制。超出授权范围的操作必须另行获得许可。

**模式 C：每次执行前确认**

任务到期后，系统通过交互端申请本次执行权限。只有在用户确认后才能启动执行。

执行确认应设置有效期。超过有效期未获得授权，默认跳过本次执行并反馈用户；周期任务则按照规则进入下一周期。

三种模式均需在创建摘要中明确展示，并支持后续修改。涉及扩大权限范围的修改必须重新获得用户确认。

### 3. 存储模块

设计用于持久化保存定时任务及其执行历史的数据库。

应记录任务详情、用户 ID、触发时间、重复规则、执行方式、权限范围、确认策略、任务状态、执行历史及其他必要信息。

采用**任务状态与执行状态分离**的设计：

任务状态描述整个任务的生命周期，例如活跃、暂停、已完成、已取消。

执行状态描述每一次触发的处理过程，例如待触发、等待授权、排队中、执行中、成功、失败、超时、跳过或取消。

一个周期任务可以保持活跃，同时存在多次成功、失败或超时的历史执行记录。

默认活跃任务列表只展示尚未结束的任务。已经完成或取消的任务不再出现在该列表中，但应保留必要的历史记录，允许用户追溯查询。

所有任务均应与创建者的用户 ID 关联，并在任务管理、历史查询和执行授权等环节执行用户权限校验。

### 4. 调度与状态管理模块

采用 Python 实现定时调度与状态管理，将原定时模块和扫描模块的职责统一协调。

调度部分负责计算任务下次触发时间、识别到期任务、发出执行信号，以及管理单次和周期任务的时间规则。

状态管理部分负责检查任务是否可执行、确认授权状态、更新每次执行记录、计算下一周期时间，并处理成功、失败、超时、跳过及取消等结果。

系统应在任务创建或修改后更新调度安排，在预定时间触发任务，并在执行结束后及时完成状态更新。

同时设置定期检查机制，用于发现遗漏调度、超时执行、授权过期和异常中断的任务。

应考虑以下异常情况：

- PC 关机、休眠、网络断开或服务重启导致错过执行时间。
- 多个任务同时到期，或同一周期任务的上一次执行尚未结束。
- 程序异常退出后恢复运行。
- 重复调度可能造成同一任务被重复执行。
- 用户在等待授权或执行过程中取消、修改任务。

错过执行时间时，应根据任务预设策略决定补执行、跳过或重新申请授权，不得在恢复运行后无条件执行全部过期任务。

调度应以持久化任务记录为依据，避免同一次任务重复执行。

定时触发功能最多使用三个进程或线程，合理分配调度与执行资源。任务超过并发容量时，应进入等待队列，不阻塞普通对话。

### 5. 执行模块

任务到期且满足授权要求后，由执行模块调用大模型，并根据任务内容选择合适的 Skills、MCP Tools 和其他可用执行能力。

提交给大模型的最终 Prompt 应采用固定范式，明确任务目标、触发原因、时间要求、必要上下文、允许的工具、目录及操作权限、执行限制和预期输出。

任务执行必须遵循当前授权范围。文件和工具访问权限应由实际执行端校验，不能仅通过 Prompt 限制。

执行的最高轮数和时间限制应与普通对话任务保持一致。每次任务执行均应有独立的执行状态和结果记录。

执行成功、失败或超时后，应及时在交互端反馈任务结果、实际完成情况及必要的错误信息。任务生成的文档或其他文件，应说明其保存位置或提供相应访问方式。

### 6. 统一日志

保留**一份定时触发功能日志**，记录该功能生命周期内的全部重要事件，不另设独立审计日志。

通过事件类型区分任务创建、查询、修改、删除、调度触发、授权申请、授权结果、执行开始、执行结束、状态更新、周期重排、异常恢复及其他必要事件。

日志应能够关联任务、具体执行记录及相关用户，记录必要的时间、事件结果和错误信息。

调度与状态管理模块产生的事件，以及执行模块返回的结果，均应完整记录在该日志中，以便定位执行失败、重复触发、权限问题及异常状态。

## 三、功能树与生命周期

### 1. 用户交互端

用户通过明确命令或自然语言发起定时任务的增删改查。

创建、修改和删除均须由用户最终确认；查询直接执行。

创建或修改时，系统应展示具体任务内容、时间及周期规则、授权模式、权限范围和必要的执行约束。

如果任务需要在执行时再次授权，则应在实际触发时间申请本次执行权限，而不是提前获得无限期授权。

任务结果和必要的状态变化应通过原交互端向对应用户反馈。

### 2. PC 端任务管理

PC 端持久化记录任务及其执行历史，区分活跃任务和已结束任务。

单次任务执行结束后，应更新任务状态，并从默认活跃任务列表移出。

周期任务在某次执行成功、失败或超时后，均应立即向用户反馈本次结果，并按照预设周期计算下一次执行时间，不因单次失败默认终止整个任务。

若任务达到约定重复次数、结束日期或被用户取消，则结束后续调度，并保留历史记录。

重复次数默认指计划触发次数。实际执行次数、执行成功次数以及因未授权而跳过的次数应予以区分，避免产生计数歧义。

### 3. 任务调度流程

用户确认创建任务后，系统写入任务记录并安排下一次触发。

任务到期时，调度模块检查任务状态与权限模式：

- 仅提醒：向用户发送提醒。
- 预授权自动执行：检查预授权是否有效，符合要求则进入执行队列。
- 每次执行前确认：向用户发送本次授权申请，等待用户决定。

用户授权后，执行模块根据固定 Prompt 和实际权限范围运行任务。

每次执行结束后，系统记录结果、反馈用户，并更新任务状态和下一次触发时间。

定期检查机制负责处理异常中断、错过触发时间、过期授权及其他遗留状态。

## 五、后续迭代

### 条件监控与复合工作流

在本轮定时触发功能完成和验证后，再考虑事件或条件触发，例如监控指定文件变化、定期检查网页信息是否更新，并仅在满足特定条件时执行任务。

进一步支持多个任务之间的依赖、执行结果传递、多步骤授权和复合工作流编排。

本轮不将上述功能纳入 MVP，以优先验证定时任务的交互、授权、执行和反馈闭环。
